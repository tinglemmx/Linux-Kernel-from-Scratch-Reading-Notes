这段代码是一个典型的 x86 实模式引导扇区（Boot Sector）汇编程序，和《从零开始写 Linux 内核》一类教程中的早期 Linux 启动代码非常相似。

它的核心任务是：把自己从 BIOS 加载的位置复制到另一个内存地址，加载后续的 Setup 程序，显示一条提示信息，最后跳转到 Setup 程序执行。

你可以先把它理解成一个非常小的操作系统启动加载器（Bootloader）。

## 一、先看整体执行流程

### ① BIOS 加载引导扇区

通常加载到物理地址 0x7C00

### ② 复制引导代码

从 0x7C00 复制到 0x90000

rep movsw：复制 512 字节

### ③ 设置段寄存器和栈

CS / DS / ES / SS / SP

### ④ BIOS 磁盘中断 int 0x13

把后续 4 个扇区读入内存 0x90200

### ⑤ 显示提示信息

Setup has been loaded

### ⑥ 跳转到 Setup

CS:IP = 0x9020:0x0000

先记住三个关键概念：

- 段寄存器：实模式下，CPU 通过段地址和偏移地址计算内存地址。
- BIOS 中断：在操作系统接管硬件之前，借用 BIOS 提供的磁盘读写、屏幕输出等服务。
- 远跳转（far jump）：不仅修改指令指针 `IP`，还修改代码段寄存器 `CS`。

下面逐段拆解。

## 二、开头的常量是什么意思？

```
SETUPLEN = 4

BOOTSEG = 0x7c0
INITSEG = 0x9000
SETUPSEG = 0x9020
SYSSEG = 0x1000

ENDSEG = SYSSEG + SYSSIZE
```

这些是汇编时使用的符号常量，类似 C 语言中的宏或常量定义。它们本身不会在运行时占用内存。

| 常量                  | 含义               |
| ------------------- | ---------------- |
| `SETUPLEN = 4`      | 要读取的 Setup 扇区数   |
| `BOOTSEG = 0x7C0`   | 原始引导代码所在的段地址     |
| `INITSEG = 0x9000`  | 复制后引导代码所在的段地址    |
| `SETUPSEG = 0x9020` | Setup 程序加载的段地址   |
| `SYSSEG = 0x1000`   | 后续系统代码的预期加载段地址   |
| `ENDSEG`            | 后续系统代码内存区域的结束段地址 |

这里的 `SYSSIZE` 没有在你贴出的代码中定义，所以 `ENDSEG` 需要依赖其他源文件或汇编参数中的定义。并且，当前代码还没有实际使用 `ENDSEG`。

### 为什么段地址看起来很奇怪？

在 x86 实模式下，通常使用下面的公式计算物理地址：

\\[ \text{物理地址}=\text{段地址}\times16+\text{偏移地址} \\]

例如：

| 段地址      | 偏移地址     | 物理地址      |
| -------- | -------- | --------- |
| `0x07C0` | `0x0000` | `0x07C00` |
| `0x9000` | `0x0000` | `0x90000` |
| `0x9020` | `0x0000` | `0x90200` |

因此，`BOOTSEG = 0x7C0` 对应的物理地址就是 `0x7C00`，也就是 BIOS 通常放置引导扇区的位置。

注意：段地址和物理地址不是同一个概念。

## 三、第一步：跳转到指定的代码段

```
.code16
.text

.global _start
_start:

    jmpl $BOOTSEG, $start2
```

逐行理解：

- `.code16`：告诉汇编器按照 16 位代码模式生成指令。
- `.text`：指定代码段。
- `.global _start`：将 `_start` 符号导出，让链接器等工具可以识别它。
- `_start:`：程序入口标签。
- `jmpl $BOOTSEG, $start2`：执行远跳转，目标为 `BOOTSEG:start2`。

这里的 `jmpl` 是 AT&T 汇编语法里的远跳转形式，`l` 表示远指针使用 32 位操作数形式；但在 `.code16` 下，具体编码仍需结合汇编器和反汇编结果确认。它不是普通的 `jmp`。

为什么需要远跳转？

因为普通跳转通常只改变 `IP`，远跳转则可以同时设置 `CS` 和 `IP`，让 CPU 使用指定的代码段执行。

不过，这条指令并没有完成从 `0x7C00` 到 `0x90000` 的复制。真正的复制发生在后面。

## 四、第二步：把引导扇区复制到新位置

```
start2:
    movw $BOOTSEG, %ax
    movw %ax, %ds
    movw $INITSEG, %ax
    movw %ax, %es
    movw $256, %cx
    subw %si, %si
    subw %di, %di

    rep
    movsw
```

这是整段代码最值得理解的部分之一。

### 1. 设置源地址和目标地址

```
movw $BOOTSEG, %ax
movw %ax, %ds
```

把 `BOOTSEG` 放进 `AX`，再将它写入 `DS`。

执行后：

```
DS = 0x07C0
```

接下来：

```
movw $INITSEG, %ax
movw %ax, %es
```

设置目标段地址：

```
ES = 0x9000
```

在 x86 汇编中，`$` 表示立即数，`%` 表示寄存器。这是 AT&T 语法，与 Intel 语法的写法不同。

### 2. 设置复制的起点和长度

```
movw $256, %cx
subw %si, %si
subw %di, %di
```

执行后：

```
CX = 256
SI = 0
DI = 0
```

这里：

- `DS:SI` 是源地址。
- `ES:DI` 是目标地址。
- `CX` 是重复执行的次数。

`subw %si, %si` 看起来有些奇怪：自己减自己，结果必然为零。这里就是用来清零 `SI` 的，`DI` 同理。

### 3. 为什么 `movsw` 复制 512 字节？

```
rep
movsw
```

`movsw` 每次复制一个 word，也就是 2 字节。

`rep` 表示重复执行，直到 `CX` 减到零。

因此：

\\[ 256 \times 2 = 512\text{ 字节} \\]

具体来说，相当于：

```
源地址：      DS:SI = 0x07C0:0x0000
目标地址：    ES:DI = 0x9000:0x0000
复制长度：    512 字节
```

### 复制前后的内存布局

源内存

## 0x7C00

512 字节

目标内存

## 0x90000

512 字节

源区域的数据被复制到目标区域，原始数据仍然保留。

有个容易忽略的细节：`movsw` 默认受方向标志 `DF` 影响。这里没有执行 `cld`，所以代码隐含依赖 `DF=0`，即复制后 `SI` 和 `DI` 递增。传统 BIOS 引导环境通常满足这一前提，但严谨的启动代码可以显式执行 `cld`。

## 五、第三步：切换到复制后的代码执行

```
jmpl $INITSEG, $go

go:
    movw %cs, %ax
    movw %ax, %ds
    movw %ax, %es
    movw %ax, %ss
    movw $0xFF00, %sp
```

这一步完成控制权转移，并设置运行环境。

### 1. 远跳转到新位置

```
jmpl $INITSEG, $go
```

将执行位置切换到：

```
CS = 0x9000
IP = go 对应的偏移
```

这里的 `go` 是标签。CPU 开始执行的是已经复制到新位置的那份代码。

为什么要复制后再跳转？

这样做可以把原始引导区域和后续加载操作所用的内存区域分开，避免后续操作覆盖仍需要执行的代码。

### 2. 设置数据段和栈

```
movw %cs, %ax
movw %ax, %ds
movw %ax, %es
movw %ax, %ss
movw $0xFF00, %sp
```

由于远跳转已经设置 `CS = 0x9000`，因此：

```
DS = 0x9000
ES = 0x9000
SS = 0x9000
SP = 0xFF00
```

其中：

| 寄存器     | 作用                  |
| ------- | ------------------- |
| `CS:IP` | 指向当前正在执行的代码         |
| `DS`    | 默认数据段               |
| `ES`    | 额外数据段，这里用于磁盘读取的目标地址 |
| `SS:SP` | 栈段和栈顶               |

栈的初始物理位置为：

\\[ 0x9000 \times 16 + 0xFF00 = 0x9FF00 \\]

栈向低地址方向增长，所以 `SP=0xFF00` 表示初始栈顶位置，而不是栈的长度。

## 六、第四步：使用 BIOS 读取 Setup 程序

```
load_setup:
    movw $0x0000, %dx
    movw $0x0002, %cx
    movw $0x0200, %bx
    movb $SETUPLEN, %al
    movb $0x02, %ah
    int $0x13
    jnc ok_load_setup
```

这段代码通过 BIOS 的 `int 0x13` 服务读取磁盘扇区。

### 1. 先理解 BIOS 磁盘读取参数

这里使用的是传统 BIOS 的 CHS 磁盘寻址方式，参数分别放在不同寄存器中。

| 指令                    | 结果           | 含义          |
| --------------------- | ------------ | ----------- |
| `movw $0x0000, %dx`   | `DH=0, DL=0` | 磁头 0，驱动器 0  |
| `movw $0x0002, %cx`   | `CH=0, CL=2` | 柱面 0，扇区 2   |
| `movw $0x0200, %bx`   | `BX=0x0200`  | 目标偏移地址      |
| `movb $SETUPLEN, %al` | `AL=4`       | 读取 4 个扇区    |
| `movb $0x02, %ah`     | `AH=2`       | BIOS 磁盘读取功能 |

最后：

```
int $0x13
```

相当于请求 BIOS 执行磁盘读取。

由于之前已经设置 `ES=0x9000`，所以目标缓冲区是：

```
ES:BX = 0x9000:0x0200
物理地址 = 0x90200
```

从第 2 扇区开始读取 4 个扇区，通常就是跳过第 1 扇区的引导代码，加载紧跟其后的 Setup 数据。

### 磁盘与内存的对应关系

磁盘第 1 扇区

512 字节

引导扇区（Boot Sector）

BIOS 负责先加载

磁盘第 2～5 扇区

2048 字节

Setup 程序

由本段代码调用 int 0x13 加载到 0x90200

### 2. 为什么读取失败后要重试？

```
jnc ok_load_setup
```

`jnc` 的意思是 Jump if No Carry，也就是当进位标志 `CF=0` 时跳转。

BIOS 磁盘读取约定是：

- `CF=0`：操作成功。
- `CF=1`：操作失败。

如果失败，程序继续执行下面的代码：

```
movw $0x0000, %dx
movw $0x0000, %ax
int $0x13
jmp load_setup
```

`AH=0` 对应 BIOS 磁盘复位功能，尝试复位磁盘系统，然后重新执行读取操作。

注意，这里没有重试次数限制。如果磁盘读取一直失败，程序就会无限循环。这是早期简单引导代码常见的处理方式，并不适合所有现代启动环境。

## 七、第五步：调用 BIOS 显示字符串

```
ok_load_setup:
    movw $msg, %ax
    movw %ax, %bp
    movw $0x1301, %ax
    movw $0x0c, %bx
    movw $21, %cx
    movb $0, %dl
    int $0x10
```

这里使用 BIOS 视频服务 `int 0x10`，调用 AH=`0x13` 的字符串输出功能。

### 关键寄存器

| 寄存器       | 值            | 含义                |
| --------- | ------------ | ----------------- |
| `AH`      | `0x13`       | 输出字符串功能           |
| `AL`      | `0x01`       | 输出后更新光标，字符串包含字符属性 |
| `BH`      | `0x00`       | 显示页面 0            |
| `BL`      | `0x0C`       | 字符属性，通常为亮红色前景     |
| `CX`      | `21`         | 字符数量              |
| `DH`、`DL` | `0`、`0`      | 行号 0、列号 0         |
| `ES:BP`   | `0x9000:msg` | 字符串的内存位置          |

字符串定义为：

```
msg:
    .ascii "Setup has been loaded"
```

这段字符串刚好有 21 个字符。

`movw $msg, %ax` 把字符串标签的偏移地址放入 `AX`，然后复制到 `BP`。这里依赖 `DS` 和 `ES` 已经设置为 `0x9000`。

有个细节需要注意：`int 0x10` 的 `AH=0x13` 功能要求字符串数据的格式与 `AL` 指定的模式一致。这里 `AL=1`，表示字符串字符后面带有属性字节；但 `.ascii` 只提供了普通字符，没有为每个字符提供属性字节。因此，按标准 BIOS 视频服务约定，这里的 `AL=1` 与字符串格式并不匹配。如果想输出纯字符串而统一使用 `BL` 指定属性，通常应将 `AL` 设置为 `0x01` 以外的模式 `0x00`（字符串不带属性，但不更新光标）或 `0x03`（字符串不带属性且更新光标）——具体选择要结合目标 BIOS 的调用约定；对本代码而言，若需要更新光标且使用统一颜色，应使用 `AL=0x03`。

## 八、第六步：跳转到 Setup 程序

```
jmpl $SETUPSEG, $0
```

这是整个引导扇区的最后一步。

它将执行位置设置为：

```
CS = 0x9020
IP = 0x0000
```

计算物理地址：

\\[ 0x9020 \times 16 + 0 = 0x90200 \\]

正好是前面磁盘读取时的目标地址。

因此，CPU 会从 `0x90200` 开始执行刚刚加载的 Setup 程序。

这里还有一个重要的概念：读取磁盘数据和执行磁盘数据是两件不同的事。 `int 0x13` 只是把数据放入内存，远跳转才将 CPU 的执行位置切换到该内存区域。

## 九、最后的 `.org 508` 和引导扇区签名

```
.org 508

root_dev:
    .word ROOT_DEV

boot_flag:
    .word 0xaa55
```

这部分决定引导扇区的尾部格式。

### `.org 508` 是什么意思？

它告诉汇编器：将当前位置调整到当前节内偏移 508 的位置。中间不足的空间由汇编器填充。

接下来：

```
root_dev:
    .word ROOT_DEV
```

写入一个 16 位的根设备标识。这里 `ROOT_DEV=0`，因此写入的两个字节都是 `0x00`。

然后：

```
boot_flag:
    .word 0xaa55
```

写入引导扇区签名。

x86 使用小端字节序，因此 `.word 0xaa55` 在磁盘上对应：

```
偏移 510：0x55
偏移 511：0xAA
```

也就是常见的 `55 AA` 引导签名。

| 偏移        | 长度     | 内容           |
| --------- | ------ | ------------ |
| `0～507`   | 508 字节 | 引导代码、字符串及填充  |
| `508～509` | 2 字节   | `root_dev`   |
| `510～511` | 2 字节   | 引导签名 `55 AA` |

前提是这段代码作为引导扇区从偏移 0 开始汇编，且前面没有其他内容占据空间。

## 十、把整段代码串起来理解

用接近伪代码的方式表示，这段程序的逻辑就是：

```
// BIOS 已经将引导扇区加载到物理地址 0x7C00

copy_memory(0x7C00, 0x90000, 512);

// 从新位置继续执行
set_stack(0x9000, 0xFF00);

// 通过 BIOS 读取磁盘第 2～5 扇区
while (read_disk_sectors(2, 4, 0x90200) fails) {
    reset_disk();
}

// 显示提示信息
print("Setup has been loaded");

// 跳转到 Setup 程序
jump_to(0x90200);
```

这不是可以直接编译运行的 C 代码，而是为了帮助你理解汇编程序的控制流程。

建议你下一步重点掌握三个东西：

1. `DS:SI` 和 `ES:DI`：理解内存复制指令如何确定源地址和目标地址。
2. `AH/AL` 与 `int 0x13`、`int 0x10`：理解 BIOS 中断如何通过寄存器传递参数。
3. `CS:IP` 与远跳转：理解 CPU 如何从引导代码切换到 Setup 程序。

掌握这三点后，再去阅读后续 Setup 代码时，就能清楚地区分：程序在什么内存位置运行、数据被加载到哪里，以及 CPU 什么时候真正开始执行加载后的代码。
